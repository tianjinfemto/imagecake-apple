# 与像素蛋糕（PixCake）的能力差距

像素蛋糕是面向商业摄影的 AI 修图软件（厦门像甜科技），核心卖点不是"功能多"，
而是**一条交付链路**：即拍 → 即修 → 即排版 → 即选 → 即交付。本文按这个链路逐项对照，
并把差距分成四类，因为"差多少"和"为什么差"是两个问题：

| 差距类型 | 含义 | 处理原则 |
|---|---|---|
| 🟦 入口缺口 | 算子/引擎已经在仓里，但没有入口，用户拿不到 | 本轮补齐（成本最低、价值最直接） |
| 🟩 算法缺口 | 能用确定性算子做出来，不依赖新权重 | 本轮补齐（离线可断言就写） |
| 🟨 权重缺口 | 需要额外模型（服装分割、天空分割、妆容/发型解析…） | 不做假实现；列清单，缺件点名 |
| 🟥 平台/产品缺口 | 联机拍摄、云端协作、在线选片、账号计费 | 与"全本地、无服务"的立场冲突，明确不做 |

> 本文件与 [parity.md](parity.md) 的分工：那张表对照的是 `imagecake`（C++ 引擎，
> 我们的能力基线）；这张表对照的是**商业产品像素蛋糕**，比 imagecake 多出运营链路
> 与逐脸自适应。两张表都成立才算"没有偷偷缩小范围"。

## 1. 人像精修（像素蛋糕最核心的一栏）

| 像素蛋糕 | 本轮之前 | 本轮之后 | 类型 |
|---|---|---|---|
| 中性灰磨皮（平整 / 立体两种模式） | ❌ 只有全局降噪（双边滤波） | ✅ `BeautyEngine.smoothPass` 频率分离：只平滑低频、高频纹理按力度保留（满力度仍留约 45%）；`smoothMode` 0=平整 / 1=立体 | 🟩 |
| 祛除瑕疵（痘印/斑点/油光） | ❌ | ✅ `blemishPass`（与邻域低频之差超阈值的孤点填掉）+ `deShine`（亮 + 失饱和才压） | 🟩 |
| 肤色统一 / 祛红血丝 | ❌ | ✅ `tonePass`：在「亮度 + 红绿轴 + 蓝黄轴」的对立色空间里把色度收敛到**局部均值**；祛红只收回偏红的一半，不整体偏绿 | 🟩 |
| 美白（脸部 / 身体分区） | ❌ | ✅ 皮肤掩码内 `L ← L + k·(1−L)`；`SkinMask` 用「色域 ∧ 人像 α ∧ 人脸框」把脸与身分开，各有独立力度 | 🟩 |
| 自动找皮肤 | ❌ | ✅ `SkinMask`（色域 + α + 关键点三层约束，缺哪层就点名哪层：`[no_constraint]`） | 🟨（更准需要皮肤分割网络；色域方案的失败模式已在注释与断言里写明） |
| 亮眼 / 牙齿美白 / 唇色 / 腮红 | ❌ | ✅ `RegionEnhance`：478 点派生虹膜椭圆、唇环、两颊 → 区域掩码 → 对立色修改；瞳孔核心不抬、高饱和唇线不当牙齿 | 🟩 |
| 祛黑眼圈 / 祛法令纹 / 颈纹妊娠纹（专项） | ❌ | ✅ 同层三个专项目：下睑椭圆内"比局部亮度均值暗出来的那一段"只抬不压；两条旋转椭圆带（鼻翼→嘴角）内只填"比低频邻域暗得多的细线"，低频阴影逐比特不动；颈纹/妊娠纹复用**同一个** `thinDarkLinePass`，选区由用户涂（`[no_line_region]`） | 🟩（**不含眼袋/眼纹几何重建**：那是体积/分割问题。颈纹**不做自动检出**：区分纹与结构阴影（锁骨、孕肚轮廓）的信息图里没有，自动抹会把人抹扁） |
| 眼镜祛反光 | ❌ | ✅ `lensWeights`（以**虹膜半径**为尺度外推的镜片区）+ `antiGlarePass`：只压"比邻域低频亮出 0.06 且低饱和且够亮"那一段，只降不升且压不成洞 | 🟩（不编造反光底下的颜色——那张图里没这个信息；偏振/厂商能力不在范围） |
| 逐脸独立美化（合影里每张脸都处理 + **逐脸不同力度**） | ❌ 只处理面积最大的那张脸 | ✅ 贯穿三段：`ShapeWarp` 逐脸往同一张位移场累加；`RegionEnhance` 逐脸栅格化后**取大**合并（重叠处不翻倍）；`SkinMask` 按 N 个脸框分脸/身。力度再按脸缩放：`face_strength.scales`（下标=面积序的第几张脸，0…200%，100=跟随全局），ShapeWarp 走逐脸 `scaled(by:)`、RegionEnhance 走逐脸权重（两者等价：位移都是 `amount × weight` 的线性函数） | 🟩（只缩放靠关键点的那两组：皮肤磨皮/美白不拆，否则脸与脸之间会出现质感不一致；身形不属于任何一张脸。下标是按位置的，换图/重测后面板自动取消选中） |
| 主题妆容（眼影/眉形/唇形模板） | ❌ | ✅ `MakeupEngine`：5 个内置模板（裸妆/红唇/烟熏/韩系/只妆眉眼），每个 = 唇环 + 上睑晕染带 + 眼线带 + 眉线带（+ 腮红）的**区域×颜色×浓淡**组合；区域全部由 478 点派生，亮度只按 `lumaKeep` 靠一部分所以唇纹与眉骨阴影不会被关闭 | 🟩（眼窝线/发丝级边界仍需分割权重；半闭眼时上睑弧退化就整层不跑） |
| 面部重塑：推颧骨/收下颌/三庭五眼/大眼/缩鼻翼/微笑唇 | ❌（手动液化可用，但没有"按骨骼推"） | ✅ `ShapeWarp` + `WarpField`：关键点 → 语义锚点（`FaceGeometry`）→ 位移场 → 一次重采样；6 个脸型项 | 🟩 |
| 美体：增高/长腿、细腰、瘦腿、天鹅颈、直角肩 | ❌ | ✅ 17 点 → `BodyAnchors` → 同一条位移场底座；增高是真正的分段纵向拉伸（髋线为锚，锚线以上逐比特不动） | 🟩 |
| "亚毫米骨骼点定位" | 部分：478/17 点网络已在清单里，但只用于智能构图 | ✅ 关键点结果进 `ImageDocument.faceGeometries` / `bodyAnchors`（**逐张脸**、按面积排序），预览与导出共用；凑不齐 478 点的那张直接丢弃；一张都没有才点名 `[no_landmarks]` / `[no_pose]` | 🟩 |
| 逐脸独立美化（合影里每张脸都处理） | ❌ 只处理面积最大的那张脸 | 见上一行（已合并：逐脸处理 + 逐脸力度一起算） | 🟩 |
| 手部美化 / 头发美化（含**换发色**、**祛碎发**） | ❌ | ✅ 手：`VNDetectHumanHandPoseRequest`（系统自带、零权重）取关节点 → 凸包 → 再与皮肤色域相与（指甲与手里的物件不会被顺手磨平）。发：头部框 ∧ 非皮肤色域 ∧ 额头线以上/脸侧带 → 软阈值去毛躁（真发丝逐根保留）+ 高光 roll-off / 提光泽 + 发色饱和；**换发色**在发区内只推 A/B 不动亮度（单轴位移夹 0.22）；**祛碎发**用三角窗环带 `1−|2w−1|/0.35`，只动掩码边缘那一圈 | 🟩（手：凸包会把指缘一小圈背景圈进来，所以力度偏温和。发：齐肩短发与衣领交界仍会误判；换发色只给 6 个真头发能有的预设色，不给自由拾色器） |
| 衣物祛褶 | ❌ | ✅ `GarmentEngine`：二频段分离（base 模糊 1.2%、deep 再模糊 5%），只把 base 的低频推向 deep，`source − base` 那段（布纹/织纹/印花边缘）逐比特带回。选区由用户涂（`BrushState.garments`），没涂不跑并点名 `[no_garment_region]` | 🟨 **换正装仍不做**：要服装分割 + 生成式合成；全自动识别"褶子 vs 接缝/图案/腰带阴影"也需权重 |
| 衣服祛褶 / 换正装 | ❌ | 祛褶见 §1（涂区 + 二频段）；换正装仍不做 | 🟨 换正装需服装分割 + 生成权重（imagecake 侧同样未接线） |
| 黑眼圈/法令纹专项 | 无专项项 | ✅ 见本表第 6 行：由关键点派生的两个专项目（逐脸），不再靠"磨皮顺手解决" | 🟩 |

## 2. 色彩与画质

| 像素蛋糕 | 本轮之前 | 本轮之后 | 类型 |
|---|---|---|---|
| 70+ 滤镜 + 本地 `.cube` | ❌ 文档里写"v1 不做" | ✅ `LUTParser`/`CubeLUT`（红最快的枚举顺序、三线性插值、1D 表逐通道、序列化往返）+ 8 个内置风格 + `.cube` 导入落盘 | 🟩 |
| 滤镜强度可调 | — | ✅ 原像素与查表结果线性混合，0 = 逐比特原图 | 🟩 |
| AI 追色（样片 → 客片） | ❌ | ✅ `ColorTransfer`：在仓里既有的对立色空间（L/A/B）上做一阶/二阶统计量对齐 `x' = (x − 本图均值)·(参考std/本图std) + 参考均值`，再按强度混合；参考图只取统计不合成也不对齐，所以不重采样。三条防炸各自一条断言：std 下限锁增益 1（纯色墙不许被追成斑块）、增益夹 0.55…1.8、恒等轴逐比特跳过。皮肤保护按色域只减色度位移不动亮度位移 | 🟩/🟨（**只对齐均值与标准差，不匹配直方图形状**：样片双峰而客片单峰时追完只是调性像而影调不像；真解是直方图规定化，断层风险高，本版不做） |
| AI 色彩风格（8 种） | ❌ | 部分：内置 8 个确定性风格（青橙/胶片/黑白/奶油/冷调/暖调/漂白/正片）。**不是模型推荐**，不自适应 | 🟨 自适应推荐需要逐图的评分模型 |
| 镜头校正（畸变/色差/暗角） | ❌ | ✅ `LensEngine.applyGeometry`（径向映射 + 逐通道色差） | 🟩 |
| 相机/镜头配置文件库（1000+ 机型） | ❌ | ❌ 手工参数代替 profile 库 | 🟨 需要一个 profile 数据库与厂商数据 |
| RAW 实时转档 | ✅（Core Image RAW + 线性工作流） | ✅ 同前 | — |
| 全链路 16bit | ✅（PNG-16/TIFF-16 自家写入器） | ✅ 同前 | — |
| 颗粒/银盐质感 | ❌ | ✅ `LensEngine.applyOverlay` 确定性哈希颗粒（同坐标同值 → 两次导出逐比特一致） | 🟩 |
| 径向 / 线性 / 画笔局部蒙版 | 只有画笔（且**没有入口**） | ✅ `LocalMask` 三形状 + 面板入口 + 画笔选区的画布手势 | 🟦 |
| 直方图 / 高光溢出警告 | ❌ | ✅ `Histogram`（R/G/B + 亮度四组，分箱与 `rgba8(dither:false)` 逐比特同口径）+ `ClippingOverlay` 溢出高亮叠层（红=高光死 / 蓝=暗部死）+ 底栏 `[clipping]` 警告；入口在「调色」首栏与画布 | 🟦→✅ |

## 5. 这两轮顺手修掉的真实缺陷

1. **旋转/翻转/裁剪点了没反应**：`ImageDocument.render()` 从未消费 `geometry`，
   面板只是把值显示出来。现在几何在渲染链最前作用到线性图上，并有逐比特断言
   （`PipelineWiringTests.testRotationChangesRenderedCanvasBitExactly`）。
   附带发现并修掉：`GeometryEngine.rotate(_:degrees:)` 之前对每个像素按通道各调一次
   `ImageSampling.bilinear`（该函数一次写 4 个通道），症状是**颜色串通道 + 最后一个像素越界写**。
2. **三块"哑资产"**：`BatchQueue`、`CollageEngine`、`LocalAdjustmentEngine` 有实现、有断言，
   但 UI 里没有任何入口 —— parity 文档还写着"LocalAdjustmentPanel 提供入口"。
   第一轮接上了本地调节与批量，并把那句不存在的描述改掉；**本轮把最后一块
   （拼图）也接进了「工具」面板与导出链**——哑资产至此清零。
3. **合影只磨一张脸**（本轮修）：`faceGeometry` 是单值字段，派生时只取面积最大的那张
   脸——症状是"一家四口只有小孩的脸被磨过"。现在 `faceGeometries` 是数组，
   位移场/区域掩码/皮肤脸身分层全部逐脸累加（断言钉住第二张脸真的动）。
4. **拼图排版会默默把主图重复填坑**（本轮在设计阶段就拦住）：图不够时
   `CollageEngine.compose` 返 nil，导出链写 `[collage_short]` 并且**不改变输出**；
   要重复必须显式勾「用主图重复填满」。
5. **唇色/牙齿美白点了没反应**（本轮 CI 第一轮才暴露的真缺陷）：
   `RegionRaster.polygon` 把**归一化**的关键点坐标当像素扫描——一个
   0.43…0.57 的唇环在 100px 画布上盖不到一个像素，于是牙齿与唇色两个
   算子永远拿到空掩码。引擎现在先乘画布尺寸再扫描（与 `disk` 拿像素半径
   不矛盾：盘是"给定位置与大小"，多边形是"关键点的位置"）。
   同一轮还按实际语义修正了两处从来没真正跑过的断言：smoothstep 盘的
   "中心满"是 251（像素中心采样）而不是 255，证件照的宽高比必须在**像素空间**
   比而不是在归一化矩形上比。
6. **`touched = touched || applyFaceEdits(...)` 会短路**（本轮 CI 第二轮暴露，
   逐脸美化自己的 bug）：第一张脸返回 true 之后，后面每张脸的**函数调用**
   都被 `||` 跳过——写法看起来与"累加"无异，症状恰好就是本要修的那个
   （合影只动最大那张脸）。现在先取进局部变量再合并，并且有一条断言
   拿"两张脸的场"与"一张脸的场"逐像素作差，而不是只测第一张脸。

第三批（妆容/头发/手部/衣物/天空/打光/慢门/联机）又掘出 5 个，其中第一个是**会崩的**：

7. **`RegionRaster.subtract` 的 UInt8 减法溢出 trap**（Signal 5）：
   `Swift.max(0, left[i] - right[i])` 两个操作数都是 UInt8，右值更大时**先 trap
   再求值**，`max(0, …)` 拦不住任何事。羽化后的唇内几乎必然在若干像素上大于
   唇环，所以 `lipWeights` 一被调用就崩 —— 唇色这个卖点从来没机会生效过。
   改成先升 Int 再减。同一个文件里的牙齿美白也依赖这个函数，算是一案两害。
8. **天空饱和上限 0.55 把真天判成"非天"**：晴天天蓝 (0.24,0.47,0.80) 在 sRGB
   上 s = 0.70。防误判的主力从来不是饱和度，而是从顶边连通生长，所以饱和度
   上限放到 0.92。这条是镜像脚本拓到的（断言自己也会红）。
9. **`SkyParameters.isNeutral` 漏了 `lightMatch`**：`!enabled || strength == 0`
   把"只借光不借天"（强度 0 + 光照匹配 100）当成整组关闭，拉光匹配完全没反应。
10. **连拍队列拿已夹范围的值比上限**：`burst` 自己已经夹到 1…60，于是
    `accepted < requested` 永远为假 —— 请求 999 张变成"默声拍 60 张"，正是本项目
    最忌讳的静默降级。计划层改成比较未夹范围的 `requestedBurst`。
11. **AVFoundation 快门回调名写错只得警告**：`capture(_:didFinishProcessing…)` 与
    协议要求的 `photoOutput(_:didFinishProcessing…)` "nearly matches"，编译器只
    给 warning 不给 error —— 症状是接得上、拍不出，最后只剩 `[camera_timeout]`。
    协议方法名写错不报错，这一类只能靠真机或断言拦。

## 7. 下一步（按"补一层就能拿到最多价值"排序）

上一轮列的 1（素材库/拼图入口）与 2（直方图）本轮已交；这轮又把五个"🟨/🟥 默认不做"的项做成了**诚实版**（妆容模板/手部/头发/衣物平整/换天空/打光/慢门/联机），并补完 P0 剩余六项（追色/眼镜祛反光/换发色/祛碎发/颈纹妊娠纹/逐脸力度）。剩下的：

1. **🟩 性能（资格线，优先于任何新功能）**：全仓只有一个 `concurrentPerform`，
   没有 vImage/Accelerate/MPS —— 40MP 上拖滑杆的卡感会一票否决其他所有优势。
   ✅ 指标已就位（`RenderPerf`：渲染 27 段 + 导出 5 段 + 预览侧 4 段，底栏「诊断」卡与导出报告 `[perf]` 行同一份数据），11 格断言钉住"没跑的阶段不出现在列表里"与"插桩不许改像素"；下一步才是真的上 SIMD/GPU 与脏区重算，而那时同一批数字就是改前改后的对照。

   **第一次实测基线（2026-11-01，run 41300357546，1024² 全效果一次渲染）**：
   中位 **81～85 秒**，最慢八段是 `region 13.1s` / `makeup 10.8s` / `skin 10.5s` /
   `hand 8.8s` / `garment 7.6s` / `denoise 7.3s` / `sharpen 6.1s` / `hair 5.9s`，而
   逐像素的 `tone` 只有 1.5s、恒等 `geometry` 是 0.00ms（顺带证明"恒等整段跳过"
   这条承诺真在生效）。**但这批数字全部是 Debug 构建（`-Onone` + 数组越界检查）
   下量的，它描述的是开发模式，不是交付给用户的 App** —— 拿它推"必须上 SIMD/GPU"
   是不成立的。这一点不是事后找借口，而是当场付过学费的：据此把三个模糊核的垂直
   pass 从列主序改成行主序（每列维护窗口和、递推序列逐个不变所以逐比特相同），
   334 格仍全绿（证明改法安全），但 `blurred` 从 3.90 变成 4.06 µs/px ——
   **量不出收益，于是整体回退**（`4636b5e`）。Debug 下越界检查占主导，本来就读不出
   内存访问模式的账。

   所以第 2 步的正确做法是先让测量本身可信，这一步已经落地：
   ① 每张计时表与 `[perf]` 行都自带 `[DEBUG]` / `[RELEASE]` 标签
      （`RenderPerf.buildConfig`），并有断言钉住"少了标签就算测量无效"；
   ② 新增 `macos-perf-release` job（只在 workflow_dispatch 时跑，因为 macOS 分钟
      按 10× 折算额度）：Release 配置下只跑三个基准类并把表打印进 job 日志；
   ③ 一条**自证式**断言代替凭感觉的毫秒阈值：可分离滑窗模糊的耗时对半径应当近乎
      不敏感，所以"半径 8 倍 → 耗时 8 倍"直接判 O(N·r²) 回归（实测比值 1.11，
      通过 —— 也就是说"算法量级错了"这个猜测同样被否掉了）；
   ④ 常驻基准尺寸 256²（1024² 一次 85 秒会把每轮 CI 拖成 5 分钟自残），
      大图的数留在本段里当历史。

   **Release 侧的数（2026-11-01，run 41308253959，`macos-perf-release` job）**：
   256² 全效果一次渲染中位 **102.3ms**（同一份代码在 Debug 下是 6040~6444ms ——
   **差 60 倍**，所以"必须上 SIMD"那个判断确实是被 Debug 数字带偏的）。
   Release 分段占比：`skin 15.2%` / `garment 14.2%` / `hand 13.9%` / `region 13.6%` /
   `hair 9.1%` / `makeup 8.5%` / `bodyLine 6.8%` / `denoise 4.9%`，而 `tone` 只占
   0.8%、`sharpen` 1.0%（Debug 里 sharpen 是 6.8%）：逐像素小算子在 Debug 下被
   越界检查惩罚得最重，两张表排序因此不同 —— 这也正是 Debug 的原语表会把人
   引向"内存访问模式"这种错方向的原因。
   原语层面：`skinApply` 0.24 µs/px 最贵；六个热段共用的 `blurred` 0.09~0.11 µs/px，
   半径 2→16 只涨 1.18 倍（再次确认是 O(N) 滑窗，不是量级错）；`geometry` 与
   `protectionMask` 仍是 0.00ms（恒等跳路有效）。
